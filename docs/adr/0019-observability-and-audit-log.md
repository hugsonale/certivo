# 0019. Observability and the audit log (P0-13)

**Date:** 27 October 2026
**Status:** Proposed

## Context

Step P0-13 asks for structured JSON logs with request IDs, metrics (request rates, latency, per-endpoint
errors, packet lag), tracing hooks, an append-only audit log for key, policy and credential changes
(Doc 9 section 8), and a dashboard and alert for error rate and packet ingestion lag.

Constraints that shape the choices: one developer; no production environment yet (P1-17); Constitution
gates (Privacy First: no secret, credential or personal data in logs; Security First: the audit trail must
resist tampering by the application); and a rule from the guide that no number may be presented as validated
before it has been measured.

## Options considered

**Logging.** (a) Python's standard `logging` with a JSON formatter we own. (b) A structured-logging
library (structlog). (c) Plain text logs with a log-shipper parsing them. Chosen: (a). The code already
uses standard `logging`, so every existing call becomes structured with no changes, and the part that
matters for privacy (scrubbing) is a few dozen lines we can read and test in full.

**Metrics.** (a) `prometheus_client` in the API process with a token-protected `GET /metrics`, scraped by
Prometheus, shown in Grafana. (b) OpenTelemetry metrics pushed to a collector. (c) A hosted service
(Datadog, Grafana Cloud). Chosen: (a). It runs locally in `docker compose` for free, the exposition format
is a standard every hosted option can also ingest, and it adds one small dependency. (b) and (c) are not
ruled out; choosing a hosted service belongs with the first production environment (D-06, D-11).

**Audit log.** (a) Explicit `audit.record(...)` calls in each route. (b) A listener on the database session
that records changes to tracked tables as they are written. (c) Database-level triggers only. Chosen: (b)
plus database triggers that make the table append-only. With (a), a new code path that forgets the call
silently leaves no record; with (b) no code path can change a tracked table without one. The record is
written in the same transaction as the change, so the two cannot disagree.

**Tracing.** OpenTelemetry, optional and off by default, because the packages are heavy and nothing needs
traces yet. The hooks (`span()`, FastAPI instrumentation, trace IDs in logs) exist so turning it on later is
a setting, not a rewrite.

## Decision

1. **Logs** are one JSON object per line: `ts`, `level`, `logger`, `msg`, `request_id`, plus fields. The
   request ID is generated by the server for every request (a caller-supplied one is ignored, which
   prevents log forgery), returned in `X-Request-ID`, and attached to every log line written while the
   request is served, including the audit lines. Values under names like token, secret, signature,
   authorization are replaced; anything shaped like our keys or a Bearer token is scrubbed from messages
   and tracebacks. Identifier fields (names ending in `_id`) are kept. The access log never holds headers,
   query strings, bodies or network addresses. Libraries that log full request URLs at INFO (httpx) are
   held at WARNING, because a partner's webhook URL can carry a secret.
2. **Metrics** are listed in `docs/spec/base/08-observability-and-audit.md`. Labels are fixed small sets
   (route template, never the raw URL; unknown paths share one label), so a scanner cannot create unbounded
   series. `/metrics` requires a bearer token outside dev and is not served at all without one.
3. **Packet ingestion lag** = the time we received a packet minus the end of the interval it describes.
   Live packets and buffered batch uploads are separate series (`via`), and the alert looks only at live
   packets: batch uploads after an outage are late by design and are already disclosed as coverage gaps.
4. **The audit log** (`audit_events`, migration 0008) records partner, API key, policy, webhook endpoint
   (including secret rotation, never the secret) and attestation signing key changes, with actor, time and
   request ID. The database refuses UPDATE, DELETE and TRUNCATE on it. Details hold names, scopes and counts,
   never secrets, key hashes, or webhook URL paths.
5. **Device registrations and SDK session tokens are not audited.** They happen once per end-user device or
   call, so they are operational data, not administrative changes. Revisit with the Trusted Device Layer (P1-02).
6. **Alerts** (`ops/prometheus/alerts.yml`) are tested with `promtool test rules`, and a Python test
   fails if a rule or dashboard panel names a metric that does not exist.

## Consequences

- Easier: finding what happened to one request (search its `request_id`); proving who changed a key or policy;
  seeing error rate and lag at a glance; every alert has a test that makes it fire.
- Every threshold (5% error share, 10 s p95 lag, minimum traffic) is a **PLACEHOLDER**. No traffic has been
  measured. They must be set from measured data, and the lag threshold agreed with the first design partner.
  No claim about speed or reliability may cite them.
- The audit table has no foreign keys and its rows outlive what they describe; test cleanup deliberately skips it.
- Metrics counters live in one process. Run one API process per scrape target, or move to the client
  library's multiprocess mode first. The Celery worker exports no metrics yet; it logs in the same JSON format.
- A database superuser can still remove the triggers. The real defence is a production database role that
  cannot, plus shipping the log to storage the application cannot write to. Both belong to P1-17 and are
  **not done**.

## Still open (not decided here)

- **How alerts are delivered** (email, chat, pager) and who is on call: with P1-17 and P1-23.
- **Retention of logs and of the audit log.** No period is set. This is a privacy decision (P0-52), like the
  score-event retention in ADR 0015. Until it is decided, nothing deletes audit rows.
- **Where logs are shipped and stored** in production.
- Whether the audit log needs a tamper-evident hash chain. Not built: it would serialise every audited write.
