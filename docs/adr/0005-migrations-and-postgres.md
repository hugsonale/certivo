# ADR 0005: Alembic migrations, and rules that keep SQLite and Postgres in step

- **Date:** 2026-10-10
- **Status:** Accepted
- **Decision register / step IDs:** P0-03, P0-04, D-11

## Context

Until now the app created its own tables on startup, tests ran only on SQLite, and Postgres (the production target) was untested. A real database holds data that must survive changes, so the schema needs a reviewed, versioned history. Postgres and SQLite also behave differently in a few places that matter to us.

## Options considered

1. **Keep creating tables from code:** simple, but gives no history and cannot change a table that has data.
2. **Hand-written SQL scripts:** works, but nothing checks that they match the models.
3. **Alembic migrations, with a check that models and migrations agree:** standard for SQLAlchemy, and the check catches forgotten migrations.

## Decision

Option 3.

- **Alembic is the only way the schema is created or changed.** Migrations are numbered by hand (`0001`, `0002`, ...). Constraints and indexes use a naming convention so later migrations can alter them. The baseline `0001` matches the models as of Build Spec 0.
- **Development migrates itself; nothing else does.** With `CERTIVO_ENV=dev` the app runs the migrations at startup. In any other environment the app never changes the database and refuses to start unless it is already at the latest revision. Migrations are a deliberate step in a deployment.
- **JSON columns are JSONB on Postgres** and plain JSON elsewhere.
- **Global policies get a partial unique index.** A normal UNIQUE constraint treats NULLs as different from each other on both databases, so two "global" policies (no partner) with the same use case and version would have been allowed. The partial index closes that gap, and the default-policy seeding tolerates two app instances starting together.
- **CI runs everything on both databases.** The full test suite runs on SQLite and on Postgres 16. `alembic check` fails the build if `app/models.py` and the migrations disagree. A smoke test starts the real Docker Compose stack (Postgres and the API), runs a scripted call, and checks the attestation signature.

## Consequences

Changing a model now needs a migration in the same pull request, and the check enforces it. A migration that has been applied anywhere except a developer's own computer must never be edited; a new one is added instead. Autogenerated migrations must be read before committing (a renamed column appears as drop plus add). Existing local dev databases built before this change must be deleted once, because they have no migration history. Daily partitioning of the score-events table remains a future migration (Doc 12 section 4.1).
